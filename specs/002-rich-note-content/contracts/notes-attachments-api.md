# Contract: Nextcloud Notes attachment endpoints (as consumed by the client)

Extends `specs/001-pocketbook-notes-mvp/contracts/notes-api-v1.md`. Same base URL rules, same
authentication (HTTP Basic with the app password), same TLS verification, same redirect handling
(credentials are never forwarded to another host), same error classification. Behavior reference:
the public Notes API description and routes (read for behavior only). Items marked **[PROBE]**
are checked against a real server by a task in `tasks.md` (and may change the fallback shown).

Base for attachments: `<server_url>/index.php/apps/notes/api/v1.4/attachment/<noteId>`
Gate: used only when the stored API versions contain `1.4`; otherwise the app reports
`unsupported_server` for attachment actions and does nothing else differently.

`<noteId>` is the **server** id of the note the attachment belongs to (a note that has never
reached the server has none; see research R-3).

## Requests

| Operation | Request | Success | Failure mapping |
|-----------|---------|---------|-----------------|
| Download | `GET …/attachment/<noteId>?path=<percent-encoded relative path>` | 200, body = file; `Content-Length` may be present | 404 → `not_found`; 400 → `unsupported_server`; 401/403 → credentials rejected (aborts as for notes); 503 → maintenance; other 4xx/5xx → `rejected` |
| Probe size | `HEAD` same URL, 3 s total timeout | 200 with `Content-Length` → size | 404 → `not_found`; no length or any other status → size unknown (not an error) **[PROBE]** |
| Upload | `POST …/attachment/<noteId>`, `multipart/form-data`, one field `file` (original file name as the part's file name), no other fields | 200, JSON `{"filename":"<relative path>"}` e.g. `.attachments.12/photo.png`; the server may have changed the name to keep it unique | 413 / `rejected` → `too_large` when 413, else `rejected`; 400 → `unsupported_server`; 401/403, 503 as above |

Rules:

- The `path` query value is the reference exactly as validated in `data-model.md` (decoded once,
  then percent-encoded as a query value). The client never invents or normalizes paths.
- Download streams to a `.part` file; the client aborts when `Content-Length` or the received bytes
  exceed 10 MiB (`too_large`) and deletes the part file. A completed download is renamed.
- Upload refuses a file over 10 MiB or missing/unreadable before any request.
- Response bodies, file names and paths are never written to logs (spec FR-033); only counts and
  the error class are.
- The upload response's `filename` is validated like any reference (relative, no control
  characters, ≤ 1,024 characters) before it is stored; an invalid answer is treated as `rejected`.
- Neither request carries `If-Match`: attachments are immutable files, not conditional resources.

## Not used

`DELETE …/attachment/<noteId>?path=` exists on the server and is deliberately not called: removing
server files is out of scope (spec assumptions). Legacy flat attachment names (Notes 6.0 and
older) work unchanged because the reference is used as written.
